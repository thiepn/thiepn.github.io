# H15 — TMS60 Faith integration

H15 is a staged private Home card, backed by a TMS60-owned Supabase RPC. The public build keeps `PUBLIC_HUB_TMS60_PRIVATE` empty, managed OAuth unconfigured, and the provider registry default-off. No OAuth clients are registered or enabled by this change. H20 remains the real-device and activation gate; project-wide raw-table, Storage and existing definer-RPC qualification is still required before issuance.

The card selects one of seven canonical translations. Account `/hub/tms60` exposes separately revisioned Summary, Continue and Search choices per translation only in a `VITE_HUB_TMS60_ENABLED=staged-v1` fixture. Revoking a connection or its underlying app-data grant permanently clears every translation's Hub permissions. Reconnection cannot resurrect an old revision.

The existing managed Supabase public-client PKCE flow is reused. OAuth bearer and rotating refresh tokens remain in RAM. Single-use pending state/verifier metadata is stored in sessionStorage for at most ten minutes; translation-qualified keys keep returns isolated. Shared callback capture scrubs protocol parameters once and routes only the matching pending state. Every read uses the canonical PostgREST endpoint, which verifies the JWT, followed by current client allowlisting, live session, account lifecycle, app entitlement and exact purpose/revision/translation checks in SQL. Decoding token claims in the browser only rejects invalid values; it never grants authority.

Summary matches native TMS60 metrics: only stage-6 wording/reference schedules whose phase is not new and due time has passed contribute review tasks. A verse with both tasks due contributes two tasks and one unique verse. Stages 1–5 remain active learning; stage zero contributes new verses. Counts use all 60 canonical entries; displayed references are bounded to ten. Continue shows recently practised references and their last reviewed dimension, not a fabricated resumable session. Search matches references only, with a POST body, a 256-character limit and twenty results. The projection returns no verse text, answers, word statistics, events, custom verses, backup contents or sync payloads.

Missing cloud state is unconnected; unsupported schema or malformed progress is unsupported. An empty search is empty. Snapshots expire within five minutes and token expiry. Reads share a per-owner 60/minute budget across translations, a one-second SQL timeout, and a two-second client deadline. Identity changes, translation changes, Hide Home, tab backgrounding, reload and disconnect discard private results and managed tokens. Expiry clears results and requires a new server check.

Links use `https://tms60.thiepn.dev/#hub=translation%3Averse%3Adimension`. TMS60 scrubs the fragment and loads the exact translation without changing the saved preference. A failed translation load never opens a different translation. The landing dialog shows the requested reference and an explicit practice button; navigation itself does not start practice or change a stage/review. The service worker includes the entry parser in its updated offline cache.

The migration denies every OAuth client raw TMS60 sync and backup tables using restrictive RLS while preserving first-party sync. Existing backup restoration was a SECURITY DEFINER bypass: its implementation moves into the private schema and the public signature now checks first-party identity before calling it. Other existing project-wide definer APIs remain a release qualification requirement.

Validation: actual SQL through PGlite, comparison against native `metrics()`/`due()` source, consent revisions, translations, owner/session/client/expiry rejection, permanent revocation, raw-table denial, first-party restore compatibility and shared rate limiting. Account UI/parser tests cover explicit choices and translation changes. Browser fixtures build the actual Hub and Account and serve actual TMS60 source; all network data are fictional and unmatched requests are blocked. No production user records are read in testing.
